# BYD Proximity Lab V1 规格

Status: ready-for-agent

原始项目目标、功能构想和场景细节见[项目目标与 V1 需求基线](requirements-baseline.md)。V1 的实施范围和验收口径以两轮讨论确认后的本规格为准。票据和依赖见[实施索引](map.md)。

## 问题陈述

作为比亚迪宋 PLUS DM-i 2024 荣耀版车主，我希望知道手机从远处走近自己的车时，能否在合适的位置可靠地产生一次接近事件。手机锁屏、放入口袋、停在车边、经过旁边同款车，或车辆进入休眠时，收到的 BLE 数据可能出现波动、空窗或身份不确定。缺少可重复的采集和回放，难以区分车辆广播、Android 扫描、目标关联和算法各自造成的问题，也无法根据实测调整参数。

## 解决方案

开发一款离线运行的 Android BLE 接近感知与算法实验 App。用户人工绑定目标，查看原始与滤波后的 RSSI，记录定点、行走和实时模拟测试 Session，并用不同算法配置回放同一段数据。一次实时模拟测试先确认 `FAR`，再确认 `NEAR`，通过本地 `ENTERED_RANGE`、界面提示、震动或通知记录模拟解锁。事件不会发送车辆指令。

交付分两类验收。实验工具用可控 BLE 数据验证采集、回放、状态与事件行为。目标车型用指定车辆和手机单独验证锁车休眠、目标关联及锁屏接近。目标车型的广播条件不足时记录未通过及实际表现，实验工具仍按其验收结果交付。

## 用户故事

1. 作为测试者，我希望扫描附近的 BLE 设备，以便从车辆和通用 BLE 设备中选择实验对象。
2. 作为测试者，我希望看到设备名、RSSI、可取得的地址、Service UUID、Manufacturer Data 与最近发现时间，以便判断哪些是候选设备。
3. 作为车主，我希望看到比亚迪候选提示，以便更快找到值得检查的设备。
4. 作为车主，我希望手工确认并绑定一个目标，以便当前监测聚焦在我选择的设备上。
5. 作为车主，我希望目标地址变化后仅在有唯一关联证据时继续监测，以便在标识轮换后仍能采样。
6. 作为车主，我希望候选冲突时看到身份不确定并保留原绑定，以便在相邻同款车等场景下决定是否重新确认。
7. 作为测试者，我希望看到权限、蓝牙和扫描状态，以便判断采集是否具备运行条件。
8. 作为测试者，我希望看到目标最近观测时间、样本数和观测间隔，以便发现丢包、空窗和数据过期。
9. 作为测试者，我希望叠加查看原始 RSSI、滤波 RSSI 与进入和离开阈值，以便观察平滑与迟滞的效果。
10. 作为测试者，我希望切换近期图表时间窗，并查看状态切换和事件标记，以便放大观察某次接近过程。
11. 作为测试者，我希望看到接近状态、运动趋势及当前算法参数，以便理解现场判定。
12. 作为测试者，我希望区分没有目标观测、扫描不可用、样本过期与已确认 `FAR`，以便定位没有触发的原因。
13. 作为测试者，我希望在车头、车尾、左右侧、主驾、副驾和后排进行定点采样，以便比较各处的信号分布和波动。
14. 作为测试者，我希望记录可选的估计距离以及手持、口袋、背包等手机放置方式，以便比较不同实验条件。
15. 作为测试者，我希望通过一次行走采样记录走近或走远过程，以便观察信号如何变化。
16. 作为测试者，我希望标记开始接近、到达期望触发位置、开始远离或离开范围等时刻，以便给回放提供参考。
17. 作为测试者，我希望将路过、车边停留等 Session 标为无需触发，以便检验误触发。
18. 作为测试者，我希望查看和筛选 Session 列表，并打开详情、图表和定点统计，以便定位可比较的记录。
19. 作为测试者，我希望修改 Session 名称或人工标签，以便修正实验上下文并保留原始观测。
20. 作为测试者，我希望删除不再需要的 Session，以便管理本地数据。
21. 作为测试者，我希望测试中断后仍能打开已保存的数据并看到中断状态，以便知道哪些内容可用于诊断。
22. 作为测试者，我希望选择 `Baseline` 或 `EMA`，以便比较原始 RSSI 判定与平滑后的判定。
23. 作为测试者，我希望新建、编辑、复制或删除具名算法配置，并选择当前生效配置，以便开展可重复的参数实验。
24. 作为测试者，我希望历史记录保留当次算法和参数快照，以便在配置编辑或删除后解释原结果。
25. 作为车主，我希望主动开启一次模拟测试并从 `UNKNOWN` 开始，以便独立验证本次接近过程。
26. 作为车主，我希望已确认 `FAR` 后走到 `NEAR` 时收到一次模拟解锁提示，以便知道触发发生在哪里。
27. 作为车主，我希望停留在 `NEAR` 时只触发一次，确认回到 `FAR` 后折返可以重新触发，以便检验事件去重和重新允许触发的行为。
28. 作为车主，我希望冷启动就在车边、扫描中断后回到车边或身份存疑时看到对应状态而没有模拟解锁提示，以便识别证据不足的情况。
29. 作为测试者，我希望锁屏并把手机放入口袋后继续当前测试，以便验证真实携带条件下的采集和提示。
30. 作为测试者，我希望在事件历史中查看时间、目标、配置版本、RSSI 和触发原因，以便追溯当时为何产生模拟事件。
31. 作为测试者，我希望分别查看模拟事件与通知结果，以便判断故障出在接近判定还是 Android 通知。
32. 作为测试者，我希望回放能够保留原始样本的时间关系和采集空窗，以便检验数据过期和恢复时的判定。
33. 作为测试者，我希望在同一 Session 上对比一套或多套配置，以便看出算法差异。
34. 作为测试者，我希望结合人工参考标记查看提前、按时、迟到、漏触发和重复触发，以便评价触发时机。
35. 作为测试者，我希望未标记的 Session 仍显示状态和事件，以便在缺少评分依据时查看观测结果。
36. 作为测试者，我希望升级后仍能查看历史结果和新回放所用版本，以便解释结果变化。
37. 作为车主，我希望测试全程在本机完成，以便无需登录账号、提供车辆钥匙材料或连接车辆。

## 实施决定

### Android 技术基线

- 固定 `minSdk = 31`（Android 12）、`compileSdk = 37`（Android 17）、`targetSdk = 36`（Android 16）。使用稳定 SDK 平台、Gradle Kotlin DSL、Gradle Wrapper 和 Version Catalog。Android 模块使用 AGP 9.x 内置 Kotlin，Compose Compiler 与实际 Kotlin 编译器对齐，Room 通过 KSP2 生成代码。JDK 优先 21。固定版本、依赖来源和初始化验证见 [Android 技术基线](android-toolchain.md)。
- 使用 Kotlin、Jetpack Compose + Material 3、Jetpack ViewModel、Kotlin Coroutines + Flow / StateFlow、Room / SQLite 和 Android BLE API。Compose 运行库与 UI 测试组件由同一稳定 BOM 管理。依赖只选对当前票有用的正式稳定版本。
- 用普通构造器和明确接口分开 Android BLE 适配、Session 存储、纯 Kotlin 接近判定与本地反馈。ViewModel 暴露可观察的 UI 状态。图表可以限频或裁剪展示数据，原始 Session 采集按独立链路完整记录。App 本地离线运行，无账号、服务器或 `INTERNET` 权限需求。

### Android App 与目标观测

- 界面围绕设备、实时监控、采样、算法实验室四项任务组织。重点验证 Android 12 真机，并兼顾 Android 14–17 的系统行为差异。较新系统 API 仅在相应版本可用时调用。
- 只读扫描允许读取标准扫描 API 提供的广播与扫描响应。扫描面向通用 BLE 设备，比亚迪特征用于发现候选设备。App 不与车辆配对、建立连接或执行 GATT 操作。`BLUETOOTH_SCAN` 使用 `neverForLocation`，V1 不推导地理坐标、不申请定位权限；若 13/14 现场发现目标广播因此被过滤，记录实际表现并重新评估权限方案。不申请 `BLUETOOTH_CONNECT`，需要的名称等字段仅从扫描记录读取。
- 一次只监测一个绑定目标。保留地址变化与关联诊断，自动延续到新地址依赖能唯一关联本车的实测证据。品牌、通用广播特征和最强 RSSI 只能辅助发现。身份无法确认时保留原绑定、输出 `UNKNOWN` 并暂停事件判定，用户可以重新确认。
- 实时图表显示原始和滤波曲线、双阈值、状态变化及可用的模拟事件标记。监控展示扫描是否可用、最近目标观测及数据是否过期。扫描已注册但没有结果时，如实显示缺少观测，避免据此断言车辆停止广播或已远离。
- 用户在 App 内主动开始采样或模拟测试。锁屏支持以用户已启动的测试为验收范围。使用标准过滤扫描和 Android 官方后台机制，按需使用 `PendingIntent`。由用户在可见页面主动开启 `connectedDevice` 前台服务，声明对应权限，在 Android 13+ 单独处理通知权限。由 11/12 验证权限、后台与通知行为，并记录设备和版本差异。记录可观测的中断、恢复、权限失效和蓝牙状态变化。进程被终止或手机重启后保留已写入的记录并标记中断。

### 接近判定与模拟事件

- `Baseline` 使用原始 RSSI，`EMA` 使用指数移动平均。两者支持可配置的进入和离开阈值，以及多帧或持续时间的证据确认。算法计算与 Android 平台、UI 和存储分离，实时和回放共用纯 Kotlin 判定逻辑。滤波、运动趋势、接近状态和事件触发资格各自有明确职责。
- `FAR` 和 `NEAR` 需要新鲜、有效且属于绑定目标的观测。接近状态采用 `UNKNOWN`、`FAR`、`NEAR`。运动趋势单独提供 `APPROACHING`、`LEAVING`、`STABLE`、`UNKNOWN`，可供算法辅助判断。车内外在 V1 用人工位置标签记录。
- 每次模拟测试从 `UNKNOWN` 开始。只有该次有效观测中先确认 `FAR`、随后确认 `NEAR` 才产生 `ENTERED_RANGE`。停留在 `NEAR` 时只产生一次，确认回到 `FAR` 后可再次触发，无独立冷却计时。`APPROACHING` 无统一强制要求。
- 扫描不可用、样本过期或目标身份失去确认时使接近状态回到 `UNKNOWN`，清除失效证据和触发资格。恢复后用新样本重新建立状态，即使先确认 `NEAR` 也不补触发。缺乏可观测 `FAR` 导致的漏触发应能从记录解释。持续确认使用独立有效观测，同一帧的重复投递不能累积证据。
- 实时监控展示状态和曲线。模拟测试启用本地事件响应，包括界面提示、震动或通知，以及带原因的事件历史。事件记录含时间、目标、算法与配置版本、判定时 RSSI 和状态转换原因。记录 App 可观测的通知结果，锁屏上是否实际呈现由真机验证。历史回放只展示该次回放输出。

### Session、算法配置和回放

- 定点与行走采样可以记录位置、可选估计距离、手机放置方式和人工参考标记。实时模拟测试保存为 Session。列表支持按设备、位置、采样类型查找，详情展示曲线和适用的统计。允许改名称、改人工标签和删除 Session，原始观测仅随 Session 管理，不能逐条编辑。
- 会话时间线保留实际供判定使用的原始 RSSI、观测时刻、App 收到时刻、目标关联和扫描变化，并能重现样本空窗、过期以及中断。采集数据、人工参考标记、算法配置与判定结果可分别管理。人工参考标记用于评价。
- 用户可管理具名算法配置并选择当前生效项，内置算法保留。开始模拟测试时固定当次配置快照，编辑当前配置从下一次测试生效。快照可在原配置改名或删除后继续解释当次结果。
- 同一判定版本、输入时间线和配置应重现语义一致的状态与事件。不同配置可以重放同一 Session。历史判定结果保留，新回放记录实际使用的算法与触发规则版本，无需长期保留所有旧算法实现。
- 一次用于评分的正样本 Session 标记一次预期接近。以人工标记和约定时间窗评价提前、按时、迟到、漏触发，并统计重复触发。明确无需触发的负样本用于统计误触发。未标记的 Session 展示状态和事件，多次往返记录可用于诊断。时间窗、试验条件和统计口径随实车样本校准并记录。

## 测试决定

- 已确认的首选入口是实时与回放共用的接近判定。在该入口提供 Session 时间线、算法和参数，断言可观察的接近状态、运动趋势、事件时间与理由。按同一输入比较实时记录与回放输出，通过固定时间线涵盖无新样本时的过期和恢复。使用真实判定逻辑，测试数据只替代 BLE 数据源、时间输入等外部边界。当前仓库尚无 Android 实现或同类测试可复用。
- 核心用例包括 `UNKNOWN → FAR → NEAR` 只触发一次、停在 `NEAR`、阈值附近抖动、确认回到 `FAR` 后折返、启动时已在 `NEAR`、只收到近端数据、重复投递同一帧、独立样本 RSSI 相同、采样空窗、停扫恢复、身份冲突及重新确认。每个用例断言对应状态及应有的事件数量。
- 从 App 的正常入口验证人工绑定、定点与行走采样、模拟测试保存、Session 筛选与标签编辑、配置复制及回放。核对改配置或删除原配置后历史快照仍可查，跨版本的回放能解释来源。检查中断记录可读、通知权限不足时事件仍可查、回放不会产生实时通知。
- **实验工具验收**以可控 BLE 设备和带标记时间线验证从扫描、采集到模拟触发、回放和对比的闭环。使用正样本和明确无需触发的样本检查统计，未标记记录只展示观测结果。
- **目标车型和手机验收**记录手机型号、Android 版本与 ROM、车辆状态、场地和放置方式。以 Android 12 为最低兼容基线；目标手机为 Android 14–17 时额外记录系统行为差异。对目标车做锁车、多个休眠阶段、重唤醒、相邻同款车、地址变化、不同方向、遮挡和车边停留试验，记录目标广播是否可见、能否唯一关联、可观测空窗及是否有足够的 `FAR` 证据。条件允许时用醒车或独立可见广播作对照，辅助区分目标未见与扫描不可用。
- 有人工标记的试验评价触发时机。单独用锁屏口袋试验观察采样、事件和通知是否实际呈现，并记录中断、恢复和电量消耗。切换蓝牙、撤销权限和系统终止进程用于验证状态与会话降级行为。对无法访问手机或车辆的情况保留实测待验状态。

## 范围之外

- 真实解锁、上锁、车辆唤醒、比亚迪账号、云控 API、数字钥匙认证、配对、GATT 和其他车控执行。
- 触发 Tasker 或其他外部自动化，BLE Beacon 正式部署与融合，自动车内外或车内座位判定，精确米级距离定位。
- `Adaptive EMA`、自动参数搜索与推荐、任意算法编辑器、AI 训练。
- 无人启动的长期后台监测、开机自启、进程终止后自动续测、厂商保活绕行、无障碍保活、Root 及全 ROM 运行承诺。
- Session 导入导出、外部脚本集成、跨手机共享、云同步和 iOS。

## 补充说明

- 交叉复审提供 Android 只读扫描和接近判定的静态技术依据。目标车型的休眠广播、身份区别能力、进入范围前的可观测性和目标 ROM 的后台行为须用真实设备验证。 [技术交叉复审](../../docs/byd-proximity-cross-review/byd-proximity-cross-review.md#9-未解决问题与验证优先级) · [领域词汇](../../GLOSSARY.md)
- 不预设 RSSI 阈值、样本间隔、触发准确率、延迟、容许时间窗或耗电上限。先建立明确的试验条件和可量化的记录方式，再按采样结果确定车型验收阈值。
- 模拟测试验证在已测输入与场景中的接近事件。实际车辆动作需要另行验证执行授权、车辆最终状态和端到端可靠性。
