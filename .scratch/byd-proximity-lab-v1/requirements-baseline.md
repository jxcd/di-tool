# BYD Proximity Lab — Android BLE 接近感知与自动化实验平台

## 一、项目背景

准备从零开发一个独立 Android App，用于通过 BLE 信号判断手机与汽车的接近关系，并为后续自动解锁提供可靠的事件触发能力。

目标车辆：**比亚迪宋 PLUS DM-i 2024 荣耀版**。

前期已经对第三方「BYD 控车」APK 进行了 Codex、DSH 独立逆向研究，以及 Codex 最终交叉复审。

请优先阅读工作区中的：

- `byd-proximity-cross-review.md`：最终交叉复审报告，作为主要技术事实依据。
- `byd-proximity-reverse-analysis-codex.md`：原始逆向报告。
- `byd-proximity-reverse-analysis-dsh.md`：原始逆向报告。

具体文件位置以当前工作区实际结构为准。

交叉复审已经确认：

1. Android 可以在不持有比亚迪账号或蓝牙钥匙材料的情况下，读取公开 BLE 广播及其 RSSI。
2. 可以利用 RSSI 滤波、迟滞、连续采样和状态机判断接近与远离。
3. BLE 地址可能变化，不能只依赖 MAC 绑定车辆。
4. 目标车型锁车、休眠后的 BLE 广播稳定性尚未经过实车验证。
5. 原 APK 存在冷启动补触发、失联判锁、弱身份自动改绑等潜在误触发风险，不应直接复刻。
6. 车内外判断可能需要额外 Beacon，目前没有足够证据保证单 BLE 信号能够可靠区分车内外。

本项目不复刻原 App，仅借鉴经过验证的通用技术机制，独立设计、实现。

## 二、项目最终目标

最终希望实现：

**手机从远处接近车辆，在到达设定的接近范围时，自动且仅一次触发车辆解锁事件。**

后续还可能增加远离车辆自动锁车、车内外判断等功能。

关键要求：

- 无需打开 App。
- 手机锁屏、放在口袋里也能够工作。
- 不依赖 Root。
- 尽量避免额外硬件。
- 准确识别目标车辆，而不是附近任何比亚迪车辆。
- 避免 RSSI 波动、蓝牙中断、服务重启等造成误触发。
- 在检测结果不确定时采用保守策略。
- 算法可通过真实采样数据持续调整和验证。

**最终目标不是精确测量车辆距离，而是在合适的接近时机可靠触发事件。**

## 三、V1 定位与范围

V1 是一个完整可使用的 **BLE 接近感知与算法实验 App**。

主要任务：

1. 搜索、识别和绑定 BLE 设备。
2. 实时监控 RSSI 及其变化。
3. 对车内外不同位置和距离进行采样。
4. 管理采样数据。
5. 配置和比较不同接近检测算法。
6. 实时推测接近状态及运动趋势。
7. 根据状态机产生模拟解锁事件。
8. 通过实时测试和历史回放评估事件触发准确性。

V1 **不执行真正的车辆解锁或上锁**。

不接入比亚迪账号、云控 API、蓝牙钥匙认证或其他车控执行功能。

V1 中的“解锁事件”仅是本地模拟事件，可以通过界面提示、震动、通知及事件日志呈现，不发送实际车控指令。

后续版本再研究真实控车适配器。

## 四、V1 功能设计

### 1. BLE 设备管理

支持：

- 搜索附近 BLE 设备。
- 显示设备名、RSSI、MAC（如果可取得）、Service UUID、Manufacturer Data 等必要信息。
- 支持人工选择并绑定目标设备。
- 对比亚迪广播特征提供辅助识别，但不限制只能扫描比亚迪设备。
- 检测 BLE 地址变化，尝试利用可验证的广播特征关联同一目标。
- 无法确认目标身份时显示不确定状态，不能仅根据 RSSI 最强自动切换目标。
- 查看蓝牙权限、扫描状态及设备最后发现时间。

V1 只进行被动扫描，不主动连接车辆，不进行 GATT 控车操作。

应考虑动态地址、广播身份不稳定、车辆休眠等情况。

### 2. 实时 BLE 信号监控

针对当前绑定设备，实时显示：

- 原始 RSSI（dBm）。
- 算法过滤后的 RSSI。
- RSSI 变化趋势。
- 当前接近状态。
- 最近一次广播时间。
- 广播间隔、采样数量和扫描健康状态。
- 当前算法及主要参数。

采用实时折线图展示：

- 原始 RSSI 曲线。
- 滤波后的 RSSI 曲线。
- 进入阈值、离开阈值参考线。
- 状态切换及模拟解锁事件标记。

支持查看最近 30 秒、1 分钟、5 分钟等时间窗口，具体交互可在设计阶段优化。

需要区分无信号、扫描停止、数据过期和真实远离。

### 3. 位置标定与数据采样

支持创建独立的采样 Session。

采样时可手工标注：

**位置：**
- 主驾、副驾、后排。
- 车头、车尾、左侧、右侧。
- 后续可扩展自定义位置。

**距离：**
- 用户目测估计的距离，例如约 1/2/3/5/8 米。
- 距离是可选估计值，不要求精密测量。
- 车内位置可不填写距离。

**手机放置方式：**
- 手持。
- 口袋。
- 背包等。

支持两种采样模式：

**定点采样**
- 在选定位置持续采样一段时间。
- 记录原始 RSSI 序列与时间戳。
- 用于分析 RSSI 分布、均值、中位数、波动程度等。

**行走采样**
- 从远处逐渐靠近车辆。
- 从车辆附近逐渐远离。
- 持续记录 RSSI。
- 用户可以手动标记关键时刻，例如：
  - 开始接近。
  - 到达期望解锁位置。
  - 开始远离。
  - 离开目标范围。

这些人工标记将用于后续算法触发效果评估。

采样时应保留必要的时间戳、设备标识、广播间隔、数据空窗及扫描状态，保证后续可回放。

### 4. 采样数据管理

V1 保持简单：

- 查看采样 Session 列表。
- 查看 Session 详情及信号曲线。
- 按设备、位置、采样类型筛选。
- 删除采样 Session。
- 必要时修改采样名称或人工标签。

不需要完整的数据编辑器。

原始 RSSI 数据应保持不可修改，防止破坏实验依据。

数据本地保存，优先使用 Room / SQLite。

采集数据与算法配置、算法运行结果分离存储，确保更换算法后能够重新分析历史数据。

### 5. 算法实验室

V1 不开发任意动态算法编辑器，也不要求训练复杂 AI 模型。

采用：

**内置算法实现 + 可管理的参数配置 + 统一评估接口。**

初步考虑三种算法：

**Baseline**
- 原始 RSSI。
- 进入/离开双阈值。
- 多帧或持续时间确认。

**EMA**
- EMA 平滑。
- 双阈值迟滞。
- 趋势或持续时间辅助判断。

**Adaptive EMA**
- 参考逆向报告中的回归残差、异常值降权、自适应 EMA、趋势和跨步约束。
- 具体算法应以交叉复审的已确认结论为依据，不必完全复制原 App。

需要支持：

- 选择算法实现。
- 为算法创建多个命名参数配置。
- 调整算法参数。
- 复制、删除用户创建的配置。
- 选择一套当前生效配置。
- 在历史数据上回放不同算法。
- 对比不同算法的接近判断及事件触发效果。

内置算法实现不可删除，用户管理的是参数配置。

自动标定可以作为 V1 的候选增强能力：根据已采样数据推荐阈值或参数组合。但不强求 V1 实现复杂的自动搜索或模型训练。

自动推荐参数时，必须避免只使用训练数据评价自身，应提供独立样本验证。

算法应尽量实现为纯 Kotlin 计算逻辑，不依赖 Android UI 或 BLE API，保证实时运行与离线回放共用同一实现。

### 6. 接近状态机

建议将以下概念分开：

**接近状态：**
- UNKNOWN
- FAR
- NEAR

**运动趋势：**
- APPROACHING
- LEAVING
- STABLE
- UNKNOWN

**车内外状态：**
- INSIDE
- OUTSIDE
- UNKNOWN

V1 核心是接近状态。

运动趋势作为辅助判断及诊断数据。

车内外状态暂时以人工采样标签和实验性推测为主，不要求第一版准确识别主驾、副驾等具体位置。

车内外判断的可靠性必须通过实测验证，不能仅凭 RSSI 较强认定在车内。

状态机需要考虑：

- 双阈值迟滞。
- RSSI 滤波。
- 连续有效样本。
- 进入与离开持续时间。
- 信号趋势。
- 扫描中断与恢复。
- 设备身份变化。
- 事件去重及冷却。
- 状态恢复与冷启动。

具体参数由算法配置管理，不提前硬编码固定阈值。

### 7. 模拟解锁事件触发（V1 核心验收）

这是 V1 最重要的功能之一。

目标事件：

`ENTERED_RANGE`

理想触发过程：

`UNKNOWN → FAR → APPROACHING → NEAR → ENTERED_RANGE`

其中 APPROACHING 是趋势，不一定是独立状态机状态。

基础原则：

1. 必须先有可信、已确认的 FAR 状态。
2. 之后确认进入 NEAR 范围。
3. 满足指定算法的有效证据后触发一次 `ENTERED_RANGE`。
4. 停留在 NEAR 时不得重复触发。
5. RSSI 临界波动不得造成反复触发。
6. 确认离开到 FAR 后，可以重新允许下次进入事件。
7. 首次启动就在 NEAR 时，不直接触发。
8. 扫描中断或重启恢复后，不能凭第一条强信号直接触发。
9. 目标车辆身份不明确时，不触发。
10. 数据不足或过期时进入 UNKNOWN，不直接视为 FAR。

真实 RSSI 不要求连续单调递增，算法可以依据滤波趋势、状态历史和多帧证据综合判断。

触发策略与 RSSI 滤波算法应解耦，以便后续更换算法时不影响事件执行接口。

V1 事件响应只支持：

- 页面显示模拟解锁提示。
- 震动或本地通知。
- 记录事件及触发原因。
- 查看事件历史。

事件应包含时间、目标设备、算法配置版本、RSSI、状态转换原因等信息。

任何事件都不得连接真实车辆控制执行器。

### 8. 实时触发测试

支持进入模拟测试模式。

用户实际走向汽车，App 根据当前生效算法产生接近状态变化和模拟事件。

需要明确显示：

- 当前状态和趋势。
- 事件触发时刻。
- 触发时 RSSI。
- 所使用的算法配置。
- 触发原因。
- 是否发生重复触发。

测试过程中即使手机锁屏，也应尽可能继续记录数据和产生模拟通知。

测试过程可以保存成 Session，用于后续分析。

### 9. 历史数据回放与算法对比

对已保存的采样 Session，支持选择一套或多套算法配置进行离线回放。

回放必须复用实时运行的核心算法及状态机逻辑。

不能为了回放另写一套简化判断逻辑。

需要支持：

- 按时间顺序重放 RSSI。
- 重现扫描空窗、时间间隔和状态切换。
- 显示模拟解锁事件。
- 对比多个算法在同一批数据上的输出。
- 使用人工标注的真实事件计算触发效果。

优先关注：

- 是否成功触发。
- 是否重复触发。
- 是否在期望位置之前误触发。
- 到达期望位置后的触发延迟。
- 漏判次数。
- 不同测试场景下的表现。

没有人工参考标注时，只展示触发结果，不虚构准确率、误判率。

### 10. 后台扫描与运行可靠性

V1 应支持基本的 Android 锁屏后台扫描与模拟触发测试。

优先使用 Android 官方机制：

- `BluetoothLeScanner`
- 必要的过滤扫描和 `PendingIntent`
- 合规的 Foreground Service
- 必要权限和系统生命周期处理

避免：

- Root 依赖。
- 无障碍服务保活。
- 过度文件权限。
- 不必要的系统权限。
- 未经验证的系统限制绕过方式。

需要记录扫描中断、恢复、权限失效等事件。

后台可靠性和电量消耗必须能够通过测试评估，不承诺所有 Android ROM 都能持续工作。

## 五、技术选型

目前已确定：

- **语言：Kotlin**
- **UI：Jetpack Compose**
- **本地数据库：Room / SQLite**
- **平台：Android 原生**
- **BLE：Android Bluetooth API**
- **架构：模块化、可测试、可扩展**

具体架构模式、依赖注入、异步处理、图表库、项目模块数量等，由后续设计确定。

要求：

1. 尽量减少不必要的第三方依赖。
2. 算法计算与 Android 平台实现分离。
3. 历史回放与实时计算共用核心逻辑。
4. 数据采集与算法配置解耦。
5. 事件检测与未来车辆控制执行器解耦。
6. 不为未来可能存在的功能过度设计。

V1 原则上本地离线运行，不需要服务器，不接入账号系统，也不需要 `INTERNET` 权限。

## 六、V1 产品界面

初步规划四个主要页面：

1. **设备**：BLE 扫描、设备列表、选择与绑定、身份诊断。
2. **实时监控**：RSSI 图表、当前算法、状态机、模拟触发及事件历史。
3. **数据采样**：位置标注、定点/行走采样、Session 管理及统计。
4. **算法实验室**：内置算法、参数配置、历史回放和算法对比。

允许在 grill 和设计阶段优化交互，但应尽量保持结构简单。

可以为后续扩展保留合理边界，但不提前实现。

## 八、V1 的核心验收目标

V1 完成后，应当能够：

1. 成功发现并人工绑定目标 BLE 设备。
2. 持续展示原始 RSSI 和过滤曲线。
3. 采集不同位置、距离和运动过程的原始数据。
4. 使用不同算法配置重放相同历史数据。
5. 根据算法输出可解释的接近状态。
6. 在已确认 FAR 后逐渐接近车辆，进入指定范围时产生一次模拟解锁事件。
7. 在 NEAR 停留、RSSI 抖动、扫描中断和恢复时避免错误或重复触发。
8. 对照人工标记评价触发时机。
9. 在目标无法确认或样本失效时明确输出 UNKNOWN。
10. 无需账号、车辆钥匙或实际控车权限即可完成全部 V1 测试。

不能预先假设触发准确率和延迟指标。

先建立可重复、可量化的测试方式，再通过真实数据确定合理验收阈值。
